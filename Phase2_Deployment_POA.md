# Parallax — Phase 2 Deployment Plan of Attack
### Cloud Deployment: AWS, GCP, Azure (in that order)

**Status:** Planning complete — AWS Terraform in progress, GCP/Azure not started
**IaC tool:** Terraform, one module per provider, `terraform destroy`-able independently

---

## 1. Goal

Deploy the containerized Parallax stack (backend + frontend, already
built and verified via Docker Compose) to three cloud providers, each
with a CI/CD pipeline triggered from GitHub, each provisioned via
Terraform for clean teardown.

This satisfies the assignment's "pick 3 cloud services, deploy,
screenshot, cost-compare" requirement, done to a higher standard than
the minimum — the team's choice to build out a fuller architecture
(network + storage + compute + secrets + CI/CD) on every platform
rather than one bare compute service each.

**The three deployments are not required to be identical.** Where a
provider's compute service has a capability another one doesn't (e.g.
Cloud Run's automatic per-request logging vs. AWS needing it configured
manually), that's a real, worth-documenting difference for the
comparison section — not a gap to force-match.

---

## 2. Resource matrix — final

| Type | AWS | GCP | Azure |
|---|---|---|---|
| Network | VPC (2 public + 2 private subnets, 1 NAT gateway) | VPC | VNet |
| Container registry | ECR (2 repos) | Artifact Registry | Azure Container Registry |
| Compute | ECS Fargate (2 services) | Cloud Run (2 services) | App Service (2 apps, container mode) |
| Load balancing / routing | ALB, path-based routing | Built into Cloud Run (auto-assigned HTTPS URL per service) | Built into App Service (auto-assigned URL per app) |
| Storage bucket | S3 — Terraform state, **plus** a separate required bucket for CodePipeline's own artifacts | Cloud Storage — Terraform state | Blob Storage — Terraform state |
| Secrets | Secrets Manager | Secret Manager | Key Vault |
| Database | Dropped — no real use case without further app changes, which aren't planned | — | — |
| CI/CD pipeline | CodePipeline + CodeBuild | Cloud Build (+ GitHub trigger) | App Service's built-in GitHub Actions deployment |
| Source connection | CodeStar Connections (GitHub) | Cloud Build GitHub trigger (native) | GitHub Actions workflow (auto-generated by App Service's Deployment Center) |
| Logging | CloudWatch Logs (app-level only by default — see note) | Cloud Logging (automatic per-request logging, no config needed) | App Service diagnostic logs (single toggle, not a Terraform resource) |
| IAM | IAM roles (task execution, task, CodeBuild, CodePipeline) | Service accounts (Cloud Run, Cloud Build) | Managed Identity (App Service) |

**Logging note:** CloudWatch Logs as configured captures container
stdout/stderr — application errors and stack traces are covered. It
does **not** capture per-request traffic (status codes, latency, path
hit counts) unless ALB access logging is separately enabled (writes to
the S3 bucket) and/or a CloudWatch dashboard is built on the ALB's
built-in metrics (`RequestCount`, `HTTPCode_Target_4XX_Count`,
`HTTPCode_Target_5XX_Count`, `TargetResponseTime` — free, since these
metrics already exist the moment the ALB exists). Cloud Run gives this
kind of traffic visibility automatically with zero configuration —
worth naming explicitly as a real difference in the comparison section,
not something to "fix" on AWS to match.

---

## 3. Database — decision log

Considered and dropped. A database with no real application using it
would be a hollow deliverable — a screenshot of an empty table isn't a
meaningful comparison point. No further backend/frontend code changes
are planned, so there's no genuine workload to justify one. This also
reduces cost risk meaningfully, since managed Postgres (RDS / Cloud SQL
/ Azure Database for PostgreSQL) is one of the pricier line items on
all three platforms.

---

## 4. Storage bucket — decision log

Each provider's bucket holds that provider's **Terraform remote state**
— a genuine, standard DevOps use with zero application code changes.
Keeping state off individual laptops also avoids the risk (already
flagged earlier in this project) of a state file with sensitive values
accidentally landing in a git commit.

AWS additionally requires a **second, separate bucket** purely as
CodePipeline's own artifact store between pipeline stages — this is a
hard AWS requirement, not a design choice, and isn't part of the
"storage service" answer for the assignment; the Terraform-state bucket
is.

---

## 5. Secrets — decision log

All three use each provider's actual named secrets service, not a
cheaper alternative, for a fairer three-way comparison:

- AWS: **Secrets Manager** (~$0.80/mo for 2 secrets — trivial against
  $100 credit)
- GCP: **Secret Manager**
- Azure: **Key Vault**

---

## 6. CI/CD — decision log

- **AWS:** CodePipeline + CodeBuild, sourced from GitHub via CodeStar
  Connections (`feature/cloud-backend` branch). Terraform draft exists,
  needs the Secrets Manager swap and state-bucket bootstrap before
  first apply.
- **GCP:** Cloud Build, triggered natively from GitHub — no separate
  connection resource needed the way AWS requires.
- **Azure:** App Service's built-in GitHub Actions deployment (via
  Deployment Center) rather than a separate Azure Pipelines setup —
  simpler, and App Service auto-generates the GitHub Actions workflow
  file itself.

**Worth naming in the comparison section:** all three technically use
GitHub as the single source of truth, but the *mechanism* differs
meaningfully — AWS needs an explicit connection resource + artifact
bucket + build spec, GCP needs just a trigger, Azure needs neither (App
Service manages the whole workflow file for you). This is a legitimate,
interesting three-way spread for the report, not an inconsistency to
smooth over.

---

## 7. Order of operations

1. **AWS** — finish Terraform (Secrets Manager swap, state bucket
   bootstrap), `terraform plan` review, apply, screenshot, `terraform
   destroy`
2. **GCP** — Terraform module, mirroring AWS's shape only where GCP
   actually has an equivalent resource
3. **Azure** — Terraform module, same approach

Each provider is deployed, screenshotted, and torn down before moving
to the next — keeps credit burn sequential and makes it obvious which
provider is costing what.
